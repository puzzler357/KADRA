## 1. Общие сведения

### 1.1. Назначение системы

Система предназначена для автоматизации кадрового учёта, управления штатным расписанием и формирования справочных документов на предприятии. Ключевое требование — современный, интуитивный интерфейс, принципиально отличающийся от интерфейса «1С:Предприятие» по эргономике, скорости работы и визуальному стилю, при сохранении возможности обмена данными с системами «1С» через файлы.

### 1.2. Ключевые характеристики

| Характеристика | Значение |
|---|---|
| Платформа | **Windows 10/11 x64** (десктоп) |
| Форм-фактор | **Только десктоп.** Опорное разрешение 1280×800, минимальное окно 1024×700. Мобильная и планшетная вёрстка не разрабатывается |
| Режим работы | 100% локальный, однопользовательский, полностью офлайн (без сети и синхронизации), включая шрифты и любые ресурсы. Единственное исключение — необязательный обмен с сервером лицензий (Р-7); данные пользователя устройство не покидают |
| Языки интерфейса | Туркменский, английский, русский |
| Язык по умолчанию | Выбирается пользователем, сохраняется локально |
| Валюта | **Настраиваемая:** символ, позиция (префикс/суффикс), число знаков после запятой, разделитель разрядов |
| Форматы выгрузки отчётов | Excel (.xlsx), JSON |
| Форматы обмена | Файловый импорт/экспорт: Excel (.xlsx), XML, CSV, Word (.docx) |
| Расчётный объём данных | До 10 000 сотрудников с сохранением отзывчивости интерфейса |
| Основной стек | React, TypeScript, Vite, Tailwind CSS, Tauri, SQLite |

### 1.3. Термины и сокращения

- **ШР** — штатное расписание.
- **Конструктор справок** — визуальный редактор шаблонов справочных документов.
- **Локальное приложение** — приложение, полностью работающее на одном устройстве без сети, внешнего сервера и синхронизации; все данные хранятся в локальной БД.
- **i18n** — интернационализация (поддержка нескольких языков).
- **Дизайн-токены** — семантические CSS-переменные (уровни фона, границ, текста, акцента), через которые задаётся всё оформление; обеспечивают согласованность и переключение тем.

### 1.4. Зафиксированные решения заказчика

Приняты 2026-08-01, имеют приоритет над любыми положениями версии 1.0.

| № | Решение |
|---|---|
| Р-1 | Целевая платформа — **только Windows**. Сборки под macOS и Linux не разрабатываются |
| Р-2 | Валюта — **настраиваемая** в модуле настроек, единая для всей системы |
| Р-3 | Форм-фактор — **только десктоп**. Мобильная и планшетная вёрстка в объём работ не входит |
| Р-4 | Требование производительности **до 10 000 сотрудников подтверждено** и входит в приёмку |
| Р-5 | Модули «Рекрутинг», «Отсутствия», «Адаптация», «Оценка», «База знаний» — **полноценные модули с хранением в БД**, а не демонстрационные экраны |
| Р-6 | **Автоматическое тестирование входит в объём работ** (принято 2026-08-23). Обязательны автотесты локального API и сквозной автоматический обход всех экранов. Отменяет вывод `TZ_AUDIT.md` о том, что e2e-тестирование несоразмерно однопользовательскому приложению — см. п. 2.6 |
| Р-7 | **Лицензирование — как в GAS** (принято 2026-10-07). Приложение работает полностью только с действующей лицензией, подписанной ключом продавца и привязанной к компьютеру; без неё — режим «только чтение»: просмотр, отчёты, печать, экспорт и резервная копия доступны, изменения отклоняются. Активация онлайн по ключу или полностью офлайн обменом файлами. Сеть используется только для обмена с сервером лицензий и никогда — для данных пользователя; отсутствие сети не блокирует работу в пределах срока файла лицензии. См. п. 2.7 и `LICENSING.md` |

### 2.2. Доступ к данным

Приложение не содержит сетевого сервера. Доступ к данным организован через **единый фасад с двумя реализациями**, выбираемыми по среде выполнения:

| Среда | Реализация |
|---|---|
| **Продуктивная сборка (Tauri)** | SQL-запросы к локальной SQLite через команды оболочки Tauri (`db_select`, `db_execute`, `db_transaction`). Соединение держит Rust (`src-tauri/src/db/`) и сверяет каждую запись с режимом лицензии; миграции и первичный посев применяет оболочка при открытии базы. Промежуточный сервер отсутствует |
| **Режим разработки (браузер)** | Локальный Express поверх той же схемы SQLite, отдающий REST на `/api/*`, совмещённый с dev-сервером Vite |

Обе реализации предоставляют интерфейсу одинаковый набор операций. Прикладной код не знает, в какой среде исполняется.

**Требования к слою данных:**
- Схема БД и начальные данные описываются **в одном месте** и используются обеими реализациями. Дублирование схемы недопустимо. Для оболочки Tauri схема собирается в `src-tauri/schema.json` командой `npm run schema:export`; автотест падает, если файл не соответствует схеме.
- В нативной сборке окно не имеет собственного доступа к базе: прав плагина SQL у него нет, запись возможна только через команды оболочки.
- Изменения схемы оформляются версионированными миграциями.
- Таблицы снабжаются индексами по полям, участвующим в фильтрации и связях.
- Доменные данные **не сохраняются в localStorage**: источник истины — SQLite, оперативный кэш — память приложения. В localStorage допустимо хранить только настройки интерфейса и признак сессии.
- Данные, растущие во времени (табели, архив), загружаются срезами по выбранному периоду, а не целиком.

### 2.3. Аутентификация

Единственная локальная учётная запись владельца устройства. Пароль хранится в виде хеша bcrypt. Ролевая модель отсутствует.

### 2.4. Библиотеки экспорта и обмена

| Задача | Технология |
|---|---|
| Генерация Excel | ExcelJS (форматирование, стили, автоширина, итоги) |
| Чтение Excel при импорте | SheetJS |
| Генерация Word | docxtemplater |
| Генерация PDF | Печать средствами оболочки; html2pdf для табличных выгрузок |
| Экспорт JSON | Нативный, по документированной схеме |
| Обмен с внешними системами | Только файловый (XML, CSV, Excel) |

> **Примечание.** Любой обмен данными выполняется через локальные файлы. Живые сетевые интеграции (в т. ч. с 1С по OData/REST), внешний сервер, синхронизация и автообновление приложения в проекте не предусмотрены — они противоречат требованию полной автономности. Обмен с сервером лицензий (п. 2.7) данными пользователя не является: передаются только ключ лицензии, хэши отпечатка компьютера, открытый ключ устройства и версия приложения.

### 2.5. Дизайн-система

Оформление задаётся семантическими токенами, а не прямыми цветами. Обязательный состав:

- **Уровни фона:** приложение → секция → карточка → вложенная карточка → контрол → усиленный контрол → поле ввода → состояние наведения.
- **Границы:** слабая / базовая / усиленная.
- **Текст:** основной / вторичный / приглушённый / едва заметный.
- **Акцент:** палитра из 10 оттенков, переключаемая пользователем.

Каждый токен определён для светлой и тёмной тем. Прямое указание цвета в коде интерфейса не допускается; исключения — печатный документ (всегда белая «бумага»), категориальная палитра графиков и цвета, применяемые пользователем к содержимому статей.

### 2.6. Автоматическое тестирование

Реализовано 2026-08-23 согласно решению Р-6.

| Уровень | Технология | Объём |
|---|---|---|
| Локальное API | Vitest | Авторизация, смена пароля, полные циклы создания / чтения / изменения / удаления по всем сущностям: сотрудники, подразделения, должности, шаблоны, табель, архив |
| Сквозной обход интерфейса | Playwright | Вход в систему, открытие каждого экрана системы, переход по всем пунктам навигации, поведение при отсутствии сессии и при неверном пароле |
| Расчётная логика | Vitest | Планируется: итоги табеля, ФОТ, занятость штатных единиц, подстановка переменных в документах, обмен через Excel, паритет ключей локализации |

Требования к тестовому контуру:

- **Одна команда для полной проверки.** Типы, сборка, тесты API и сквозной обход запускаются единой командой и дают однозначный результат «годен / не годен».
- **Изоляция данных.** Тесты работают с отдельной временной базой, создаваемой на время прогона. Рабочая база пользователя не читается и не изменяется ни при каких обстоятельствах.
- **Автономность.** Прогон не требует сети и внешних сервисов. Браузер для сквозного обхода устанавливается один раз локально.
- **Обнаружение скрытых отказов.** Сквозной обход фиксирует не только видимые поломки вёрстки, но и ошибки в консоли браузера, необработанные исключения и неуспешные обращения к локальному API — экран считается исправным только при их полном отсутствии.
- **Синхронность с кодом.** Появление нового экрана обязывает включить его в список автоматического обхода, появление нового метода API — покрыть его тестом.

> **Граница покрытия.** Автотесты Vitest и Playwright проверяют веб-режим доступа к данным. Сторона Rust нативного режима — открытие базы, миграции и посев, охрана записи, лицензирование — покрыта тестами `cargo test` в `src-tauri` (с подменой времени, отпечатка и хранилища); TypeScript-слой поверх команд оболочки (`src/data/tauriDb.ts`) автотестами не покрыт и проверяется вручную (`TEST_SCENARIO.md`, С-17).

### 2.7. Лицензирование

Реализовано 2026-10-07 согласно решению Р-7, по модели проекта GAS. Полное ТЗ — `LICENSING.md`; здесь — обязательный минимум.

| Требование | Реализация |
|---|---|
| Где проверяется лицензия | Только в Rust (`src-tauri/src/license/`). Интерфейс показывает результат и не может его изменить |
| Подлинность | Файл лицензии подписан Ed25519 ключом продавца; публичные ключи вшиты в сборку (`src-tauri/license-keys.json`), отладочный ключ — только в отладочной сборке |
| Привязка | Отпечаток компьютера (идентификатор установки Windows, плата, системный диск) — совпадение 2 из 3; ключ устройства под DPAPI |
| Тарифы | Бессрочная, годовая, квартальная — онлайн или офлайн; месячная — только онлайн |
| Две даты | «Оплачено до» (+7 льготных дней) и «файл действует до» — срок доверия онлайн-файлу (30 дней) |
| Без лицензии | Режим «только чтение» на уровне оболочки: запись в базу отклоняется в Rust. Разрешены вход, просмотр, отчёты, печать, экспорт, резервная копия. Если владелец ещё не создан — экран активации |
| Защита от перевода часов | Наибольшее виденное время в двух защищённых копиях и в журнале аудита; откат больше чем на 48 ч — «только чтение» до исправления часов, проверки онлайн или файла разблокировки от продавца |
| Активация | Онлайн по ключу `KDR-XXXXX-XXXXX-XXXXX-XXXXX`; офлайн — файл запроса `.kdrreq` → файл лицензии `.kdrlic` |
| Перенос | Деактивация на старом компьютере (онлайн или файлом `.kdrdeact`); переустановка Windows на том же компьютере — повторная привязка, не перенос |
| Сторона продавца | `license-server/` (сервер и веб-панель License Manager), `tools/kdr-license` (то же из консоли) |
| Релизная сборка | Не собирается без адреса сервера лицензий (`LICENSE_SERVER_URL`, только `https://`) и без релизного ключа подписи |

Шифрование данных с лицензией не связывается никогда: данные принадлежат пользователю.

## 3. Состав системы

### 3.1. Модули первоначального задания

1. **Кадровый учёт** — карточки сотрудников, приём/перевод/изменение оклада/увольнение, история изменений.
2. **Штатное расписание** — дерево подразделений, должности, ставки, штатные единицы, вакансии, версии ШР.
3. **Конструктор справок** — визуальное создание шаблонов, поля-подстановки, генерация документов.
4. **Отчётность** — предустановленные отчёты, конструктор отчётов, выгрузка в Excel и JSON.
5. **Файловый обмен** — импорт/экспорт Excel/XML/CSV, генерация Word.
6. **Администрирование** — язык, локальный пароль владельца, журнал аудита, лицензия.
7. **Настройки (централизованные)** — единый центр всех параметров системы (Приложение А).

### 3.2. Модули, построенные сверх первоначального задания

Введены в ходе разработки, входят в состав системы и в приёмку (решение Р-5).

8. **Табель учёта рабочего времени** — форма Т-13: буквенные коды явок, навигация по периодам, автоматические выходные, итоги по дням, явкам и часам, фильтр по подразделению.
9. **Рекрутинг** — канбан-доска кандидатов с перетаскиванием между стадиями подбора, поиск, фильтры.
10. **Отсутствия** — заявки на отпуск, больничный, отгул, удалённую работу; согласование и отклонение.
11. **Адаптация и увольнение** — чек-листы задач onboarding и offboarding с ответственными и прогрессом.
12. **Оценка персонала** — цели с прогрессом, оценочные кампании, ревью 360°.
13. **База знаний** — статьи с форматированным текстом, категории, полнотекстовый поиск.
14. **Архив** — данные завершённых периодов, фильтры по году, подразделению и сотруднику, выгрузка в Excel и PDF, печать.
15. **Профиль пользователя** — данные владельца, настройки языка и темы, безопасность.

### 3.3. Общие требования к модулям

- Данные любого модуля хранятся в локальной SQLite. Хранение доменных данных только в состоянии интерфейса не допускается.
- Каждый экран имеет состояния: загрузка, пусто, ошибка, успех.
- Все строки интерфейса выведены в словари локализации; в коде экранов текст не хардкодится.
- Каждый модуль регистрирует свои параметры в централизованном модуле настроек.
- Каждый рабочий модуль доступен из главного меню; пункт меню не ведёт на незавершённый экран.

### А.10.1. Сброс данных

Функция сброса реализуется с несколькими уровнями, чтобы разделить безопасные операции и необратимые. Каждая операция требует подтверждения; необратимые операции требуют повторного ввода пароля, фиксируются в журнале аудита и по умолчанию сопровождаются предложением создать резервную копию.

- **Сброс пользовательских настроек к значениям по умолчанию** — возвращает тему, язык, пресеты, раскладку интерфейса к исходным; данные не затрагиваются.
- **Сброс настроек модуля/системы к заводским** — откат конфигурации без удаления кадровых данных.
- **Очистка данных отдельного модуля** — удаление данных выбранных модулей (кандидаты, заявки, чек-листы, статьи, табели, архив) с явным выбором области.
- **Полный сброс системы (factory reset)** — необратимое удаление **всех** локальных данных и настроек: должны очищаться все таблицы без исключения. Двойное подтверждение (ввод пароля + фраза-подтверждение), обязательная резервная копия перед выполнением, запись в аудит.

> Частичное удаление под видом полного сброса недопустимо. Операции, поддерживающие откат, восстанавливаются из резервной копии.
