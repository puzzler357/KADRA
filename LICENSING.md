# Лицензирование KADRA

Техническое задание и справочник к коду лицензирования — обеих половин:
проверки в самом KADRA (`src-tauri/src/license/`, `src-tauri/src/db/`, экраны в
`src/`) и сервера лицензий (`license-server/`, `tools/kdr-license/`).
Комментарии в коде ссылаются на номера разделов этого файла: «(5.4)» — правило
продления, «(8.1)» — порядок вычисления состояния, «(10.1)» — таблицы сервера.

Модель перенесена из проекта GAS (`GAS_last`, `LICENSING_SPEC.md` v1.2) без
изменений по существу; нумерация разделов совпадает, поэтому одно и то же
правило в обоих проектах называется одним номером. Отличия KADRA от GAS
перечислены в 9.4.

Решение заказчика о лицензировании — Р-7 в [TZ.md](TZ.md); как этим
пользоваться продавцу — [license-server/SellerManual.md](license-server/SellerManual.md).

---

## 1. Две даты, а не одна

Различаются два независимых вопроса:

| Дата | Отвечает на вопрос | Кто её двигает |
| --- | --- | --- |
| `paid_until` | до какого числа оплачено | оплата (кнопка «Продлить» или webhook) |
| `lease_until` | до какого числа можно верить **этому файлу** | выпуск нового файла |

**Инвариант сервера:** `lease_until ≤ paid_until + grace_days`. Файл никогда не
даёт доверия дольше, чем оплачено с учётом льготных дней. Проверяется в
`assertLeaseInvariant` при выпуске каждого файла; нарушение — ошибка 500, а не
молча выпущенный файл.

Для бессрочной лицензии обе даты пустые.

## 2. Тарифы и режимы активации

### 2.1. Что продаётся

| Тариф | Срок | ONLINE | OFFLINE |
| --- | --- | --- | --- |
| `PERPETUAL` | бессрочно | да | да |
| `ANNUAL` | 12 месяцев | да | да |
| `QUARTERLY` | 3 месяца | да | да |
| `MONTHLY` | 1 месяц | да | **нет** |

MONTHLY + OFFLINE создать нельзя: обмениваться файлами каждый месяц никто не
будет. Без интернета — предоплата минимум за квартал одним файлом.

Режим — свойство **лицензии**, а не тарифа: годовую можно продать и онлайн, и
офлайн.

### 2.2. Параметры тарифа

Хранятся в таблице `plans`, заполняются значениями по умолчанию при создании
базы и дальше принадлежат владельцу: правка значений в коде не перезаписывает
изменённые в работающей базе.

| Параметр | По умолчанию | Смысл |
| --- | --- | --- |
| `lease_days_online` | 30 | на сколько дней онлайн-файл даёт доверие |
| `refresh_after_days` | 7 | через сколько дней клиент идёт за новым файлом |
| `grace_days` | 7 | льготные дни после `paid_until` |
| `warn_lease_days` | 7 | за сколько дней предупреждать об истечении аренды |
| `warn_paid_days` | 14 | за сколько дней предупреждать об окончании оплаты |
| `clock_tolerance_hours` | 48 | допуск на расхождение часов |
| `max_transfers_per_year` | 2 | переносов между компьютерами за 365 дней |

## 3. Формат лицензии

### 3.1. Конверт

```json
{ "kid": "kdr-2026-1", "payload": "<base64url байтов JSON>", "sig": "<base64url Ed25519>" }
```

Подписываются **байты `payload`**, а не «JSON вообще»: получатель сначала
проверяет подпись над байтами, потом разбирает JSON. Каноническая сериализация
не нужна.

### 3.2. Содержимое `payload`

`v`, `license_id`, `revision`, `customer_id`, `customer_name`, `product`
(`KADRA`), `edition`, `features`, `plan`, `activation_mode`, `seats`,
`activation` (`activation_id`, `device_name`, `device_pubkey`, `fp`,
`fp_threshold`), `issued_at`, `paid_until`, `grace_days`, `lease_until`,
`refresh_after`, `max_version`.

`revision` монотонен: файл с ревизией меньше уже виденной принимать нельзя —
так отсекается повтор старого файла.

### 3.3. Ключи подписи

Ed25519. Закрытый ключ лежит в зашифрованном PEM, пароль приходит из
окружения при запуске и сервером никуда не записывается. Публичная половина —
в `src-tauri/license-keys.json` под своим `kid`.

Смена ключа: новый `kid` добавляется в связку в версии N и начинает подписывать
с версии N+1. Отзыв ключа — выпуск сборки без него.

**Без закрытого ключа нельзя выпускать файлы для уже проданных копий.** Две
резервные копии на разных носителях — обязательны.

Отладочный ключ `kid = "dev"` (`src-tauri/license-keys.dev.json`) — только для
проверок; в поставку он попадать не должен.

### 3.4. Подписанный статус

Кроме файла лицензии сервер подписывает короткие статусы:

| `kind` | Когда | Содержит |
| --- | --- | --- |
| `REVOKED` | лицензия отозвана | `nonce` запроса |
| `TRANSFERRED` | место освобождено | `nonce` запроса |
| `CLOCK_RESET` | разблокировка часов, файл `.kdrclock` | `high_water_to` |

Статус тоже расходует ревизию, поэтому каждый принимается один раз.

## 4. Привязка к устройству

### 4.1. Два механизма вместе

1. **Ключ устройства.** Клиент держит свою пару Ed25519 и подписывает ею каждый
   запрос. Сервер хранит публичную половину в `activations.device_pubkey`.
2. **Отпечаток компьютера** `fp` из трёх частей: `mg` (идентификатор установки
   Windows), `smbios` (материнская плата), `disk`. Совпадение **2 из 3**
   (`FP_THRESHOLD`) считается тем же компьютером.

Одна активация = один компьютер и один профиль Windows. `seats` ограничивает
число одновременно действующих активаций.

Отпечаток хранится только хэшами `SHA-256("KDR-fp-v1" + значение)`; сырые
значения компьютер не покидают. Значения-заглушки прошивок (`00000000-…`,
`FFFFFFFF-…`, «To be filled by O.E.M.») дают пустой хэш и совпадением не
считаются. Диск — серийный номер физического диска с системным томом, а не
серийный номер тома: тот меняется при переформатировании вместе с
MachineGuid, и переустановка выглядела бы как другой компьютер.

### 4.2. Итоговая проверка на запуске

Отпечаток вычисляется заново при каждом запуске и на диске не хранится.
Ключ устройства хранится только под DPAPI (привязан к пользователю Windows на
этом компьютере): копия профиля на другой машине его не расшифрует. Файл
лицензии, скопированный на другой компьютер, даёт MACHINE_MISMATCH (тест 3).

## 5. Протокол обмена

### 5.1. Запрос — один формат для онлайн и офлайн

```
type: ACTIVATE | REFRESH | REBIND | DEACTIVATE
license_key | license_id + activation_id
device_name, device_pubkey, fp, app_version, client_time, counter, nonce
```

Подписан ключом устройства. Подпись доказывает, что запрос сделан на
устройстве с этим ключом, — и ничего больше; имеет ли оно право на лицензию,
решает сервер.

`counter` — счётчик запросов устройства. Запрос `REFRESH` со счётчиком не
больше предыдущего означает вторую работающую копию системы (клон виртуальной
машины, восстановленный образ диска). Запрос **не отклоняется**: активация
помечается `FORK_SUSPECTED` для разбора продавцом, потому что восстановленная
резервная копия — причина невинная.

Один и тот же файл запроса обрабатывается и онлайн (`/v1/activate`), и офлайн
(`.kdrreq` через панель) — одним и тем же кодом.

### 5.2. API

| Метод | Для кого | Что делает |
| --- | --- | --- |
| `POST /v1/activate` | KADRA | активация по ключу лицензии |
| `POST /v1/refresh` | KADRA | новая аренда или подписанный статус |
| `POST /v1/rebind` | KADRA | тот же компьютер после переустановки |
| `POST /v1/deactivate` | KADRA | освободить место |
| `POST /v1/payments/<источник>` | платёжная система | уведомление об оплате |
| `POST /v1/offline/inspect` | панель | что просит файл запроса |
| `POST /v1/offline/process` | панель | применить и выдать файл |

Вход онлайн-методов — запрос, подписанный ключом устройства, без сессии. Ответ —
подписанный файл лицензии или подписанный статус. **Ошибка сети, таймаут, 5xx,
неподписанный ответ ничего не меняют** — состояние клиента двигает только
подписанный ответ.

### 5.3. Продление офлайн-клиента не требует запроса

При продлении офлайн-лицензии новые файлы для всех её действующих активаций
возвращаются сразу: просить у клиента файл запроса незачем.

### 5.4. Правило продления

Где начинается оплаченный период:

- заплатил **до** конца `paid_until + grace_days` → от старого `paid_until`,
  клиент не теряет дней;
- заплатил **позже** → от даты оплаты, никто не платит за неиспользованное
  время.

Месяцы календарные, с прижатием к последнему дню месяца: 31.01 + 1 месяц =
28.02 (29.02 в високосный год). Бессрочную лицензию продлить нельзя.

## 6. Защита от перевода часов

Клиент хранит **наибольшее виденное время** (`high_water`) и сравнивает с ним.

Источники `high_water` (берётся максимум):

1. файл состояния `state.bin`, защищённый HMAC (ключ HMAC — под DPAPI);
2. вторая копия состояния в реестре `HKCU\Software\KADRA\License`;
3. `issued_at` последнего полученного файла (время **сервера**);
4. наибольший `audit_log.ts` — время последней записи журнала аудита.

Оболочка дописывает текущее время в `state.bin` и в реестр при каждом запуске и
каждые 30 минут работы, поэтому первые два источника растут и без связи с
сервером. Время из журнала оболочка читает **сама**, из базы, при запуске и
каждые 30 минут; окно в этом не участвует и не может его придержать (в GAS это
значение передавал JS — см. 9.4).

Повысить `high_water` можно, понизить — нет.

### 6.1. Ограничение на якорь из базы

**Только записи этого компьютера.** В KADRA нет синхронизации между
компьютерами, поэтому весь журнал написан на этом. Единственный путь чужих
записей в журнал — восстановление резервной копии с другого компьютера; от
сильно сбитых часов там защищает ограничение ниже.

**Ограничение сверху.** Значение якоря принимается, только если оно не больше
`max(high_water из state.bin и реестра, issued_at) + 400 дней`. Всё, что выше, —
след сбитых часов или подмены: такое значение игнорируется и записывается в
журнал аномалий.

Потолок отсчитывается от растущего `high_water`, а не от неподвижного
`issued_at`: у бессрочной лицензии через 400 дней от выпуска иначе любая
обычная запись превышала бы потолок (тест 29).

### 6.2. Пропажа состояния — это аномалия, а не чистый лист

Удалить `state.bin` и ключ реестра может любой пользователь, а `audit_log`
лежит в его собственной базе. Если считать, что после этого `high_water`
начинается заново, получается бесплатный обход: удалить два хранилища,
очистить журнал, поставить часы на день после выпуска файла.

Поэтому: **лицензия есть, а состояния нет или его HMAC не сходится** →

| Режим лицензии | Что происходит |
| --- | --- |
| ONLINE | `STATE_MISSING`: обновление с сервера; успех → состояние создаётся заново; сети нет → READ_ONLY до ближайшего успешного обновления |
| OFFLINE | `REBIND_REQUIRED`: нужен новый подписанный файл от продавца |

Ключ устройства, ключ HMAC и копия состояния лежат в одном значении реестра
под DPAPI: удалить состояние, не потеряв ключ устройства, нельзя.

### 6.3. Правило отката и выход из него

```
now < high_water − 48 ч   ИЛИ   now < issued_at − 48 ч   →   CLOCK_ROLLBACK
```

`CLOCK_ROLLBACK` означает режим «только чтение». Выходов три:

- часы исправлены на верные — состояние снимается само;
- ONLINE: успешное обновление с сервера заменяет `high_water` серверным временем;
- OFFLINE: подписанный файл `.kdrclock` (`kind: CLOCK_RESET`, поле
  `high_water_to`) от продавца, см. 3.4. Файл расходует ревизию, поэтому
  принимается один раз.

**Честное ограничение.** Полностью офлайн-программа не может доказать настоящую
дату, если пользователь полностью управляет компьютером. Механизм ловит
типичный перевод часов назад, но не абсолютно, поэтому офлайн-подписки
продаются только длинными сроками (2.1).

## 7. Перенос, повторная привязка, отзыв

### 7.1. Повторная привязка — тот же компьютер

Переустановили Windows: ключа устройства нет, отпечаток совпадает 2 из 3. Это
**не перенос**, место не теряется.

- Онлайн: автоматически — фоновая проверка или кнопка «Проверить лицензию»
  создают новый ключ и вызывают `/v1/rebind`; одобрение не нужно.
- Офлайн: «Создать файл запроса» (`REBIND`), продавец выпускает новый файл.

Больше трёх автоматических привязок одного места за 30 дней → `FORK_SUSPECTED`:
так же выглядят две машины, перетягивающие одну активацию.

### 7.2. Перенос — другой компьютер

Отпечаток не совпадает. Нужно **явное одобрение продавца**: ни `/v1/activate`,
ни `/v1/rebind` перенос сами не одобряют. Считаются все переносы и освобождения
за 365 дней; сверх `max_transfers_per_year` — только отдельным решением, с
отметкой в журнале.

Если старый компьютер работает, клиент освобождает место сам — «Настройки →
Лицензия → Деактивировать компьютер»:

- онлайн: `/v1/deactivate`; только подписанный `TRANSFERRED` с `nonce` этого
  запроса удаляет лицензию и ключ устройства;
- офлайн: KADRA сохраняет `deactivation_proof.kdrdeact` — запрос `DEACTIVATE`,
  подписанный ключом устройства, — и **только после этого** удаляет лицензию
  и ключ. В состоянии остаётся отметка: тот же файл лицензии повторно не
  импортируется.

Если старый компьютер сломан — переносит продавец, указав, какое место
освобождается.

### 7.3. Отзыв: когда он вступает в силу

| Режим | Когда подействует |
| --- | --- |
| ONLINE | при ближайшем обновлении — подписанный `REVOKED` |
| OFFLINE | только по окончании `paid_until + grace_days` |

Дотянуться до уже выданного офлайн-файла нечем. Статус `REVOKED` у лицензии и
её активаций — всё, что технически возможно: новые файлы не выпускаются.
Принятый подписанный `REVOKED` клиент помнит и после перезапуска; старый файл
лицензии его не отменяет (тест 14).

### 7.4. Что считается одним местом

**Место = компьютер + профиль пользователя Windows.** База и ключ DPAPI лежат в
профиле пользователя. Терминальный сервер с пятью кадровиками под своими
учётными записями — пять мест.

## 8. Состояния и режимы работы

### 8.1. Порядок вычисления (в Rust, `state.rs`)

```
1.  нет файла лицензии                           → UNLICENSED
2.  неизвестный kid / подпись неверна / формат   → INVALID
3.  отпечаток < 2 из 3                           → MACHINE_MISMATCH
4.  отпечаток ≥ 2, ключа устройства нет          → REBIND_REQUIRED
5.  состояния нет или HMAC не сходится           → STATE_MISSING (6.2)
6.  версия KADRA > max_version                  → VERSION_NOT_COVERED
7.  откат часов (6.3)                            → CLOCK_ROLLBACK
8.  сервер ранее вернул подписанный REVOKED      → REVOKED
9.  paid_until ≠ null и now > paid_until + grace → EXPIRED
10. lease_until ≠ null и now > lease_until       → LEASE_EXPIRED
11. paid_until ≠ null и now > paid_until         → GRACE
12. иначе                                        → ACTIVE
```

9 и 10 разделены намеренно: клиент должен понимать, что делать — **оплатить**
(EXPIRED) или **подключиться к интернету / импортировать файл**
(LEASE_EXPIRED). Состояние пересчитывается при запуске, каждые 30 минут и
после каждой операции с лицензией.

### 8.2. Режим приложения

| Состояние | Режим | Что видит пользователь |
| --- | --- | --- |
| ACTIVE | **FULL** | ничего; предупреждение за 7 дней до `lease_until` и за 14 до `paid_until` |
| GRACE | **FULL** | баннер «Подписка закончилась N дн. назад, осталось M льготных дн.» |
| остальные | **READ_ONLY** | баннер с причиной и одной кнопкой действия |
| нет лицензии и нет владельца | — | экран активации вместо приложения |

**READ_ONLY гарантирован всегда.** Разрешено: открытие базы, применение
миграций и посев, вход, просмотр, отчёты, печать, экспорт в Excel/Word/PDF,
резервная копия. Запрещено: любое изменение данных — оболочка отклоняет запись.

Экран активации показывается, пока в базе нет владельца (`users` пуста): в
режиме «только чтение» на такой базе нечего смотреть и некуда войти. Когда
владелец есть, приложение открыто для чтения.

Шифрование базы **никогда** не связывается с лицензией: данные принадлежат
клиенту, и доступ к ним не отключается из-за окончания подписки.

### 8.3. Состояния активации на сервере

| Статус | Смысл |
| --- | --- |
| `ACTIVE` | работает |
| `RELEASED` | место освобождено, файлы не выпускаются |
| `REVOKED` | лицензия отозвана |
| `FORK_SUSPECTED` | подозрение на вторую копию; работать не мешает, нужен разбор |

Подозрение снимается кнопкой в панели, с записью в журнал.

## 9. Реализация в KADRA

### 9.1. Rust: `src-tauri/src/license/` и `src-tauri/src/db/`

| Файл | Назначение |
| --- | --- |
| `license/mod.rs` | `LicenseManager`: пересчёт статуса, уведомление окна (`license://changed`) |
| `license/model.rs` | конверт, лицензия, запрос, статус, состояние на диске |
| `license/keys.rs` | встроенная связка ключей из `license-keys.json`; `dev` — только в отладочной сборке |
| `license/verify.rs` | `kid` → подпись над байтами → только потом JSON; продукт `KADRA` |
| `license/fingerprint.rs` | MachineGuid (реестр), SMBIOS UUID и серийный номер системного диска (WMI) |
| `license/device_key.rs` | пара Ed25519 устройства, подпись запросов |
| `license/store.rs` | `license.kdrlic`, `state.bin` с HMAC, хранилище под DPAPI в реестре |
| `license/clock.rs` | `high_water`, правило отката, якорь с потолком (6) |
| `license/state.rs` | порядок 8.1 и режим 8.2 |
| `license/files.rs` | `.kdrreq` наружу, `.kdrlic` и `.kdrclock` внутрь, `.kdrdeact` наружу |
| `license/client.rs` | HTTPS к серверу (reqwest + rustls, сертификаты из хранилища Windows, системный прокси) |
| `license/platform.rs` | всё, что нужно от ОС, за одним трейтом — тесты подменяют время, железо и хранилище |
| `license/commands.rs` | команды Tauri (ниже) |
| `db/mod.rs` | единственное соединение `rusqlite` (WAL) с `local-hr-docs.db` в `%APPDATA%\com.kadra.local` — там же, где его держал `tauri-plugin-sql` |
| `db/schema.rs` | миграции и посев из `src-tauri/schema.json` до вычисления режима |
| `db/guard.rs` | при режиме, отличном от FULL, проходят только чтения |

Файлы на диске: `%APPDATA%\com.kadra.local\license\license.kdrlic` и
`state.bin`, значение `Vault` в `HKCU\Software\KADRA\License`.

**Команды Tauri:**

| Команда | Что делает |
| --- | --- |
| `license_status()` | состояние, режим, даты, причина, `database_empty` — только для отображения |
| `license_refresh()` | «Проверить лицензию»: онлайн — обмен с сервером, офлайн — перечитать файлы и часы |
| `license_activate_online(licenseKey)` | онлайн-активация |
| `license_export_request(kind, licenseKey, title)` | диалог сохранения и `.kdrreq` (ACTIVATE / REBIND) |
| `license_import(title)` | диалог открытия, проверка и установка `.kdrlic` или `.kdrclock` |
| `license_deactivate(online, title)` | онлайн-деактивация или `.kdrdeact` + удаление лицензии |
| `db_select`, `db_execute`, `db_transaction`, `db_serialize` | доступ к базе через охрану |

Ни одна команда не принимает от окна ни состояния, ни режима, ни пути к файлу:
диалоги открытия и сохранения показывает оболочка (`tauri-plugin-dialog` на
стороне Rust; прав `dialog:*` у окна нет).

Адрес сервера вшивается при сборке из `LICENSE_SERVER_URL`; файл лицензии может
его переопределить подписанным полем `server_url`. Отладочная сборка по
умолчанию ходит на `http://127.0.0.1:8787/v1`, переменная
`KDR_LICENSE_SERVER_URL` подменяет адрес только в ней. Фоновая онлайн-проверка
— при запуске, если прошёл `refresh_after`, и далее раз в 12 часов. Ошибка
сети, таймаут, 5xx и неподписанный ответ ничего не меняют.

### 9.2. Окно

- `src/store/useLicenseStore.ts` — статус из `license_status`, подписка на
  `license://changed`, вызовы команд.
- `src/components/LicenseGate.tsx` — экран активации (ключ → онлайн, либо обмен
  файлами в три шага) и баннер над страницей.
- `src/components/LicenseSettings.tsx` — «Настройки → Лицензия»: владелец,
  номер, тариф и режим, компьютер, «оплачено до», «файл действует до», версии,
  последняя проверка; «Проверить лицензию», «Импортировать файл», «Создать
  файл запроса» / «Активировать», «Деактивировать компьютер».
- `src/data/shellDb.ts` — обёртка над `db_*`; отказ `READ_ONLY` превращается в
  понятное сообщение. Транзакции идут одним пакетом `db_transaction`.
- `src/store/useDatabaseStore.ts` — в режиме «только чтение» правка не
  начинается (иначе оптимистичное обновление показало бы несохранённое).

Блокировка в окне — для удобства, а не защита (9.3).

### 9.3. Где реально проходит защита

Проверка в JS — для удобства пользователя: бандл можно извлечь и изменить.
Граница — Rust, и держат её три решения; по отдельности каждое обходится.

1. **Записывает в базу только Rust.** `tauri-plugin-sql` удалён, у окна нет
   прав `sql:*`, а `guard.rs` сверяется с режимом перед каждой командой.
   Изменённый JS, вызвавший `db_execute` напрямую, получит отказ (тест 27).
   Отвергнутый вариант — выдавать право `sql:allow-execute` во время работы:
   обратной операции `remove_capability` в Tauri 2 нет, а переходы в READ_ONLY
   внутри сессии бывают (отзыв, истечение, откат часов).
2. **Схему и посев применяет Rust**, до вычисления режима и в обход охраны.
   Иначе READ_ONLY не открыл бы даже пустую базу (тест 26). Источник схемы
   один — `src/data/schema.ts`, `entities.ts`, `seedData.ts`; Rust читает
   собранный из них `src-tauri/schema.json` (`npm run schema:export`), тест
   `tests/unit/desktopSchema.test.ts` падает, если файл устарел.
3. **В десктопной сборке нет работающего пути к данным в обход оболочки.**
   Веб-режим ходит в Express (`server.ts`), который в установщик не входит:
   извлечённый из установщика фронтенд — пустая оболочка без доступа к базе.

Плюс релизный профиль: `strip`, `lto`, один codegen unit, `panic = "abort"`.
Подпись установщика сертификатом — за владельцем (нужен сертификат).

Взломать изменённым Rust-бинарником можно и это. Цель — сделать взлом дороже
лицензии, а не невозможным.

### 9.4. Отличия от GAS

| В GAS | В KADRA | Почему |
| --- | --- | --- |
| пути к файлам приходят из JS, диалоги — `@tauri-apps/plugin-dialog` в окне | диалоги показывает оболочка, команды путей не принимают | изменённый скрипт не может писать файлы куда угодно; офлайн-деактивация не отделяется от сохранения подтверждения |
| якорь времени передаёт JS (`license_report_time_anchor`), фильтр по `device_id` | якорь читает Rust из базы; фильтра нет | синхронизации между компьютерами в KADRA нет; окно не может придержать якорь |
| «пустая база» — нет проводок и счетов | «пустая база» — нет владельца | без владельца в режиме «только чтение» не войти |
| схема — `schema.sql` | схема — TypeScript, Rust читает собранный `schema.json` | в KADRA схема генерируется из описания сущностей |
| доказательство для сервера синхронизации (`license_sync_proof`) | нет | в KADRA нет синхронизации |
| `GAS-…`, `.gas*`, `HKCU\Software\GAS` | `KDR-…`, `.kdr*`, `HKCU\Software\KADRA`; продукт `KADRA` | файлы GAS не подходят к KADRA и наоборот |

## 10. Сервер и License Manager

### 10.1. Таблицы

| Таблица | Что хранит |
| --- | --- |
| `customers` | клиенты |
| `plans` | параметры тарифов (2.2) |
| `licenses` | **хэш** ключа, тариф, режим, места, `paid_until`, статус |
| `activations` | компьютеры: `fp`, `device_pubkey`, статус, счётчик, ревизия |
| `issued_files` | что и когда выпущено, с sha256 файла |
| `transfers` | переносы и освобождения |
| `payments` | оплаты: сумма, период, источник, внешний номер |
| `webhook_sources` | отправители уведомлений об оплате и их секреты |
| `events` | журнал действий продавца и запросов клиентов |
| `admins`, `sessions` | вход в панель |

Ключ лицензии хранится **только хэшем**, как пароль. Формат:
`KDR-XXXXX-XXXXX-XXXXX-XXXXX` — base32 Крокфорда, 19 случайных символов
(95 бит) и контрольный символ Luhn mod 32. Ввод прощает регистр, пробелы и
путаницу O/0, I/L/1; опечатка отсекается контрольным символом, не расходуя
попытку.

На онлайн-методах — ограничение частоты запросов с одного адреса:
`activate`, `rebind`, `deactivate` — 20 в час, `refresh` — 120 в час.

### 10.2. License Manager

Веб-панель от того же сервера, только для продавца: вход по паролю (scrypt) и
одноразовому коду (TOTP), сессия 12 часов, cookie `HttpOnly; Secure;
SameSite=Strict` плюс обязательный заголовок на изменяющих запросах. Каждый код
принимается один раз.

Клиенты, лицензии, компьютеры, офлайн-файлы, платежи, подозрительные события.

### 10.3. Утилита вместо сервера

`tools/kdr-license` делает то же из консоли тем же кодом и в базе того же
формата. Переезд на сервер — копирование одного файла базы.
