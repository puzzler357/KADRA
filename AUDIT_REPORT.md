# Технический отчёт: аудит UI/UX, дизайн-системы и локализации KADRA

**Дата:** 2026-07-22
**Объём:** визуальная система (светлая/тёмная темы, цвета, контраст, границы, фоны, единая дизайн-система) + инфраструктура локализации и навигация.

---

## 1. Общая информация

### Что проверено
- Все страницы (`src/pages/*` — 22 экрана) и общие компоненты (`Layout`, `EmployeeForm`, `EmployeeActions`).
- Дизайн-токены и слои темы (`src/index.css`).
- Файлы локализации (`src/locales/ru.ts`, `en.ts`, `tk.ts`) и точки подключения i18n.
- Конфигурация TypeScript/сборки.

### Корневая причина проблем светлой темы
Приложение было спроектировано «dark-first»: **552 захардкоженных класса `slate-*`** (тёмные оттенки как поверхности/границы, светлые как текст) не реагировали на смену темы. Через CSS-переменные менялась только оболочка (фон, сайдбар, рамка), а все карточки, поля, таблицы, модалки оставались тёмными → в светлой теме интерфейс выглядел «сломанным». `dark:`-вариантов почти не было.

**Решение:** введён семантический слой токенов (уровни фона / границы / текст) для обеих тем, и весь хардкод системно переведён на токены.

### Многоуровневая система фонов (введена)
```
Фон приложения      → bg-app        (--surface-app)
Фон секции          → bg-section    (--surface-section)
Фон карточки        → bg-surface    (--surface)
Вложенная карточка  → bg-surface-2  (--surface-2)
Контрол / шапка     → bg-surface-3  (--surface-3)
Усиленный контрол   → bg-surface-4  (--surface-4)
Поле ввода          → bg-input      (--surface-input)
Ховер               → bg-surface-hover (--surface-hover)
```
Каждый уровень визуально различим в обеих темах.

## 3. Исправления дизайн-системы

- **Добавлены семантические цвета в `@theme`** (Tailwind v4), переключаемые по теме через CSS-переменные — с полной поддержкой вариантов `hover:`/`focus:`/`group-hover:`:
  - Фоны: `app, section, surface, surface-2, surface-3, surface-4, input, surface-hover`
  - Границы: `line, subtle, strong`
  - Текст: `primary, secondary, muted, faint`
- **Определены значения для светлой и тёмной тем** (`:root` и `.dark`) — единый источник истины.
- **Убраны захардкоженные цвета из UI-компонентов:** 2 hex из осей графика (переведены на токены через CSS). 
- **Оставлены осознанно (не UI-хром, не тема):**
  - Палитра серий графика `COLORS` (Dashboard) — категориальные цвета данных.
  - Стили печатного документа в `DocumentGenerator` (`#e2e8f0`, `#f8fafc`, `bg-white text-black`) — это «бумага», должна быть белой в любой теме.
  - Цвета текста в редакторе `KnowledgeBase` (`#10b981`, `#f43f5e`) — значения, которые пользователь применяет к содержимому.
- **`border-base` переименован в `border-line`**, чтобы имя цвета `line` не конфликтовало со встроенной утилитой `text-base` (font-size) Tailwind.

## 4. Исправления локализации

### Файлы переводов (`ru.ts`, `en.ts`, `tk.ts`)
- **Единый бренд:** `app_name` приведён к `"KADRA"` во всех трёх языках (было «KADRA» / «HR & Docs Platform» / «HR & Docs Platformasy»).
- **Достигнут паритет ключей** между ru/en/tk (ранее в en/tk отсутствовали `nav.movements`, `nav.calendar` и др.).
- **Добавлены недостающие ключи навигации:** `recruiting, timeoff, timesheet, onboarding, performance, knowledge_base, generate, archive` (ранее были только частично и хардкодом в Layout).
- **Расширен `common`:** `add, edit, delete, close, confirm, export, import, back, apply, reset`.
- **Добавлен раздел `user.owner`** (Владелец / Owner / Eýesi).
- **Туркменские переводы** приведены к корректным терминам (напр. `timeoff → «Rugsatlar»`, `onboarding → «Uýgunlaşma»`, `performance → «Baha beriş»`, `knowledge_base → «Bilim binýady»`).

### Навигация полностью трёхъязычная
`Layout.tsx`: все 14 пунктов сайдбара и подпись пользователя переведены на `t('nav.*')` / `t('user.owner')` — раньше половина была захардкожена по-русски. Заголовок топбара берётся из переведённого пункта меню.

### Экран «Настройки» полностью локализован
`Settings.tsx` (самый большой экран) полностью переведён на i18n: 7 вкладок, все секции (Общие, Пароль, Безопасность, Аудит, Резервное копирование, Импорт/экспорт, Оформление), включая тексты кнопок, placeholder'ы, `alert`/`confirm`-сообщения. Добавлено **~95 ключей** в namespace `settings` × 3 языка с профессиональными формулировками (туркменский — в латинице, требует финальной сверки носителем). Демонстрационные записи журнала аудита и эндонимы языков («Русский» / English / Türkmençe) осознанно оставлены как есть.

**Паритет ключей подтверждён программно: ru = en = tk = 125 ключей, 0 расхождений.**

## Остаток работ (честная оценка)

**Постраничная локализация завершена — все 18 экранов + оболочка + компоненты форм.** Готово: `Layout`, `Settings`, `Profile`, `Employees` (+ `EmployeeForm`, `EmployeeActions`), `OrgChart`, `Recruiting`, `TimeOff`, `Timesheet`, `Onboarding`, `Dashboard`, `Templates`, `TemplateBuilder`, `Movements`, `CalendarView`, `Archive`, `DocumentGenerator`, `Reports`, `Performance`, `KnowledgeBase`.

**Ключей локализации: 440 (паритет ru = en = tk, 0 расхождений).** Весь UI-хром переведён на 3 языка; в исходниках остаются только демонстрационные/mock-данные (образцы сотрудников, статей, событий), эндонимы языков и доменные enum-коды формы Т-13 — они намеренно не локализуются. Туркменский выполнен в латинице и требует финальной вычитки носителем.

Профессиональная экстракция и перевод на английский и **носительский туркменский** — делаются по одному экрану за проход (машинный перевод наспех недопустим — ТЗ требует уровня носителя). Текущая итерация дала: инфраструктуру i18n, паритет ключей (125, 0 расхождений), единый бренд, полную локализацию оболочки и экрана «Настройки».

**Рекомендованный следующий шаг:** продолжить постранично (следующий кандидат — `Profile` или `Employees`), с финальной сверкой туркменских формулировок носителем.

## 7. Тестовый контур (добавлен 2026-08-23)

До этой даты автотестов в проекте не было вообще: единственной автоматической проверкой был `tsc --noEmit`, всё остальное проверялось глазами. Добавлены два независимых набора.

### Состав

| Набор | Файлы | Тестов | Время | Что проверяет |
|---|---|---|---|---|
| API (Vitest) | `tests/api/auth.test.ts`, `tests/api/crud.test.ts` | 19 | ~3 с | Вход, неверный пароль, несуществующий пользователь, наличие JWT, отсутствие `password_hash` в ответе, смена пароля с откатом. Чтение всех шести коллекций, camelCase-маппинг вместо колонок БД, разбор JSON-поля `blocks`, полные циклы создания → чтения → изменения → удаления по сотрудникам, подразделениям, должностям, шаблонам, табелю и архиву |
| e2e (Playwright) | `tests/e2e/auth.setup.ts`, `pages.spec.ts`, `login.spec.ts` | 23 | ~1,8 мин | Вход в систему, редирект с `/` на `/dashboard`, открытие всех 18 экранов, переход по всем ссылкам сайдбара, поведение без сессии и при неверном пароле |

Полная проверка — одной командой `npm run verify`: `lint` → `build` → `test` → `test:e2e`.

### Результат прогона

```
lint      → tsc --noEmit: 0 ошибок
build     → клиент + dist/server.cjs собраны
test      → 19 passed (2 файла)
test:e2e  → 23 passed (1,8 мин)
```

### Связь с предметом этого отчёта

Отчёт посвящён дизайн-системе и локализации, и здесь у нового контура есть прямая польза и прямая граница.

**Польза.** Наблюдатель `tests/e2e/pageWatcher.ts` объявляет экран сломанным при любой ошибке консоли, необработанном исключении или ответе ≥400. Токен-рефакторинг затронул 27 файлов и 1028 замен цвета — раньше регрессия вида «страница падает после правки класса» ловилась только ручным обходом. Теперь все 18 экранов проверяются за 1,8 минуты вместо 15–20 минут ручной работы.

**Граница — существенная для этого отчёта.** Тесты **не проверяют визуальную корректность**. Съехавшая вёрстка, неверный токен, белый текст на белом фоне, сломанная светлая тема — всё это даёт зелёный прогон, потому что ошибок в консоли не возникает. Скриншотных сравнений в контуре нет. Пункт «Адаптивность» и качество тем по-прежнему требуют человеческого глаза, и добавление автотестов этого не изменило.

**Три локализации** тоже вне покрытия: обход идёт на языке по умолчанию, паритет ключей ru/en/tk по-прежнему проверяется вручную. Автоматическая проверка паритета — очевидный следующий шаг, она дешевле остальных и закрывает регрессию, которая уже случалась.

### Правки в коде ради тестируемости

Три штуки, поведение при обычном запуске не меняющие: путь к БД читается из `DB_PATH` (`src/db/sqlite.ts`), Express экспортируется и его автозапуск отключается через `HR_NO_AUTOSTART=1` (`server.ts`), для e2e выставляется `DISABLE_HMR=true` (`playwright.config.ts`). Первая правка обеспечивает изоляцию — тесты работают на временной базе в `tests/.tmp/` и рабочую `local-hr-docs.db` не трогают.
