## 0. Роль и незыблемые правила

Ты — senior full-stack инженер, дорабатывающий **существующее** десктоп-приложение кадрового учёта KADRA. Приложение локальное, однопользовательское, офлайн: один владелец устройства, одна локальная SQLite, никакой сети (кроме необязательного обмена с сервером лицензий, см. 1.8), синхронизации, ролей и мультипользовательского режима.

**Главное правило: ничего не переписывать «с нуля».** Каждая задача ниже — точечная доработка поверх работающего кода. Прежде чем менять файл — прочитай его целиком.

**Что менять запрещено без явного запроса пользователя:**
- Систему дизайн-токенов в `src/index.css` (8 уровней фона, 3 границы, 4 текста, 6 акцентов). Она уже полностью покрывает светлую и тёмную темы — использовать её, а не хардкодить `slate-*`/hex.
- Фасад доступа к данным `src/data/index.ts` и его двухрежимную схему (Tauri / web-dev).
- Границу лицензирования (1.8): у окна нет прав `sql:*` и `dialog:*`, в базу пишет только Rust через `src-tauri/src/db/guard.rs`, команды лицензии не принимают от окна ни режима, ни путей. Не возвращать `tauri-plugin-sql` и не добавлять команд, обходящих охрану.
- Структуру трёх файлов локализации (`src/locales/{ru,en,tk}.ts`) — только дополнять, сохраняя паритет ключей.
- Стек: React 19, Vite 6, Tailwind v4 (CSS-first), Zustand, React Router 7. Никакого shadcn/ui и Radix — в проекте их нет и вводить их не нужно.

**Обязательные правила разработки:**
1. Все пользовательские строки — через `t('...')`. Хардкод русского текста в JSX — дефект.
2. Новые ключи локализации добавлять сразу в три файла (ru/en/tk), паритет ключей обязателен.
3. Новые сущности — сначала таблица в `src/data/entities.ts` / миграция в `src/data/schema.ts` (схема одна на оба режима), затем **`npm run schema:export`** (оболочка Tauri применяет миграции из `src-tauri/schema.json`; тест упадёт, если забыть), затем метод в `src/data/index.ts` и `src/data/tauriDb.ts`, затем действие в `useDatabaseStore`. Несколько связанных записей в нативном режиме — одним `db.transaction([...])`, не `BEGIN`/`COMMIT` отдельными вызовами.
4. Цвета — только токены (`bg-surface-*`, `text-primary/secondary/muted/faint`, `border-line/subtle/strong`, `accent-*`).
5. `tabular-nums` для чисел, `rounded-xl`/`rounded-2xl` для карточек — как в существующих экранах.
6. После каждой задачи: **`npm run verify`** должен проходить целиком. Это цепочка `lint` → `build` → `test` (Vitest, API) → `test:e2e` (Playwright, обход всех экранов). Отдельные шаги — `npm run lint`, `npm run build:client`, `npm test`, `npm run test:e2e`.
7. Добавил маршрут в `src/App.tsx` — сразу добавь его в `tests/e2e/routes.ts`, иначе экран выпадет из автоматического обхода. Добавил или изменил эндпоинт в `server.ts` — покрой его в `tests/api/crud.test.ts`.
8. Красный тест — это дефект в коде, а не в тесте. Ослаблять проверку (расширять список игнорируемых ошибок консоли в `tests/e2e/pageWatcher.ts`, удалять ассерт) допустимо только для доказанного шума инфраструктуры и с комментарием, объясняющим почему.

### 1.2. Двухрежимный доступ к данным (ключевое архитектурное решение проекта)

`src/data/index.ts` — единый фасад. Ветвление по `isTauri = '__TAURI_INTERNALS__' in window`:

- **Tauri (продакшн):** `src/data/tauriDb.ts` — SQL-запросы через команды оболочки `db_select` / `db_execute` / `db_transaction` (`src/data/shellDb.ts`). Соединение держит Rust (`src-tauri/src/db/`), миграции и сид применяет он же при открытии базы, до вычисления режима лицензии; каждая запись проходит `guard.rs`. Аутентификация локальная через bcryptjs, токен-заглушка `'local'`.
- **Web-dev (`npm run dev`):** `server.ts` — Express + `better-sqlite3` + Vite middleware, REST на `/api/*`, схема и сид в `src/db/sqlite.ts`, JWT для логина.

Оба слоя дают одинаковый набор функций: `listEmployees/createEmployee/updateEmployee/deleteEmployee`, то же для `departments`, `positions`, `templates`, `timesheets`, `archives` (у архивов нет update), плюс `login`, `changePassword`, `resetSystem`.

> **Осознанный долг:** схема БД описана дважды (`src/db/sqlite.ts` и `src/data/tauriDb.ts`) и уже разошлась — в `sqlite.ts` есть `ALTER TABLE` для `birth_date`/`payment_type`/`salary`/`rate`, в `tauriDb.ts` эти колонки сразу в `CREATE TABLE`, миграций нет. См. задачу 4.1.

### 1.3. Сторы

**`useAppStore`** (`persist: 'hr-docs-app-storage'`) — UI и сессия:
`theme` (light/dark/system, дефолт **dark**), `accentColor` (indigo/purple/blue/emerald/rose/amber), `density` (compact/standard/spacious), `fontSize` (small/standard/large), `language`, `sidebarOpen`, `user`, `token`.
Настройки применяются как классы на `<html>` (`applyTheme/applyAccentColor/applyDensity/applyFontSize`) и дополнительно восстанавливаются синхронным IIFE до гидратации — чтобы не было вспышки темы.

**`useDatabaseStore`** (`persist: 'hr-docs-local-db'`) — сущности: `employees, departments, positions, timesheets, archives, templates`. `fetchAll()` дёргается из `App.tsx` после логина. Мутации оптимистичные: сначала `set`, затем запрос.

Два независимых набора, обе точки входа собраны в `npm run verify`.

| Набор | Где | Чем гоняется | Что проверяет |
|---|---|---|---|
| API | `tests/api/` | Vitest 3 | `auth.test.ts` — вход, неверный пароль, несуществующий пользователь, наличие JWT, отсутствие `password_hash` в ответе, смена пароля с откатом. `crud.test.ts` — чтение всех шести коллекций, camelCase-маппинг, разбор JSON-поля `blocks`, полные циклы create→read→update→delete по сотрудникам, подразделениям, должностям, шаблонам, табелю, архиву |
| UI | `tests/e2e/` | Playwright, проект `chromium` | `auth.setup.ts` — вход один раз, `storageState` переиспользуется. `pages.spec.ts` — редирект с `/`, обход всех 18 экранов, прокликивание всех ссылок сайдбара. `login.spec.ts` — без сессии показывается форма входа, неверный пароль не пускает внутрь |

**Два контракта, на которых всё держится — их нельзя ломать:**

1. **`DB_PATH`** (`src/db/sqlite.ts`) — путь к файлу БД. Не задан → рабочая `local-hr-docs.db`. Оба набора тестов поднимают собственную временную базу в `tests/.tmp/`, поэтому рабочие данные не трогаются никогда.
2. **`HR_NO_AUTOSTART=1`** (`server.ts`) — импорт модуля без запуска слушателя. `server.ts` экспортирует `app` и `startServer`; API-тесты поднимают Express прямо в своём процессе через `app.listen(0)`, без vite-мидлвари. Отсюда весь набор укладывается в ~3 секунды.

Прочие детали, о которые легко споткнуться:

- `DISABLE_HMR=true` выставляется для e2e из `playwright.config.ts`. Без этого HMR-вебсокет vite сыплет ошибками в консоль и мешает дождаться `networkidle` — первый прогон уронил из-за него все 18 страниц.
- `tests/e2e/pageWatcher.ts` считает страницу сломанной при любой ошибке консоли, необработанном исключении или ответе ≥400. Список игнорируемого шума — там же, в одном месте.
- Список маршрутов вынесен в `tests/e2e/routes.ts` и должен совпадать с роутером в `src/App.tsx`.
- Первый запуск e2e на новой машине требует `npx playwright install chromium` (~250 МБ, один раз).
- HTML-отчёт последнего прогона: `tests/.tmp/playwright-report/index.html`. Каталог `tests/.tmp/` в `.gitignore`.

**Граница покрытия.** Тесты гоняют веб-режим через Express. Ветка Tauri (`src/data/tauriDb.ts`) автотестами **не покрыта** — при правке слоя данных её по-прежнему нужно проверять руками через `npm run tauri:dev`. Проверяется, что экраны открываются и API отвечает, а не что расчёты верны — расчётная логика ждёт покрытия в задаче 4.4.8.

**Rust — `cargo test` в `src-tauri`** (с 2026-10-07): база, миграции, охрана записи и лицензирование — 75 тестов с подменой времени, отпечатка и хранилища; `cargo test --lib -- --ignored e2e` — ещё два сквозных против утилиты `kdr-license` и настоящего сервера лицензий (нужен Node 22.18+). Сервер лицензий — `npm test` в `license-server` (55 тестов). В `npm run verify` они не входят: свои тулчейны.

**Ручной сценарий — `TEST_SCENARIO.md`.** То, чего автотесты не видят: правильность расчётов, сохранность данных при перезагрузке, читаемость обеих тем, здравый смысл цифр. 166 шагов (из них 18 — лицензирование в десктопе, С-17) на данных вымышленной организации (12 сотрудников, 5 подразделений, 17 штатных единиц), контрольные суммы посчитаны заранее и сверены по коду. Прогонять перед любой демонстрацией заказчику и после задач Приоритета 0. Меняешь расчётную логику или сид — синхронизируй раздел «Контрольные суммы», иначе сценарий начнёт врать.

### 1.8. Лицензирование (введено 2026-10-07, не ломать)

Перенесено из GAS (`D:\Бухучет\GAS_last`, `LICENSING_SPEC.md`) с той же нумерацией правил. Всё — в `LICENSING.md`; здесь — что нужно помнить при любой доработке.

- **Решает только Rust.** `src-tauri/src/license/` вычисляет состояние (порядок 8.1) и режим FULL / READ_ONLY; `src-tauri/src/db/guard.rs` отклоняет запись в READ_ONLY. Окно (`useLicenseStore`, `LicenseGate`, `LicenseSettings`) только показывает результат.
- **В READ_ONLY работает чтение, вход, отчёты, экспорт, резервная копия.** Любая новая функция, которая пишет в базу «по ходу чтения» (счётчик просмотров, отметка «прочитано»), должна переживать отказ `READ_ONLY` молча — как `audit()` в `tauriDb.ts` — иначе она сломает просмотр без лицензии.
- **Стор не начинает правку в READ_ONLY** (`blockedByLicense()` в `useDatabaseStore`) — новое мутирующее действие должно начинаться с той же проверки, иначе оптимистичное обновление покажет несохранённое.
- **Файлы и форматы:** `.kdrreq` / `.kdrlic` / `.kdrclock` / `.kdrdeact`, ключ `KDR-XXXXX-…`, продукт `KADRA`, хранилище `HKCU\Software\KADRA\License`, файлы в `%APPDATA%\com.kadra.local\license`.
- **Сторона продавца:** `license-server/` (сервер + License Manager), `tools/kdr-license` (то же из консоли), руководство — `license-server/SellerManual.md`.
- **Сборки.** `npm run tauri:dev` доверяет dev-ключу и ходит на `http://127.0.0.1:8787/v1` (сервер — `npm run dev` в `license-server`). `npm run tauri:build` требует `LICENSE_SERVER_URL=https://…/v1` и релизный ключ в `src-tauri/license-keys.json` (`node tools/kdr-license keygen --kid kdr-2026-1`; закрытая половина остаётся в `~/.kdr-license/keys`, в репозиторий не попадает).
- **Версия** одна в `package.json`, `tauri.conf.json` и `Cargo.toml` (тест `tests/unit/version.test.ts`): лицензия ограничивает версии полем `max_version`.

### Приоритет 0.5 — масштаб 10 000 сотрудников (блокирующее)

Заказчик подтвердил порог из ТЗ: **10 000 сотрудников, плавная прокрутка, основные экраны ≤ 1 с.** Текущая архитектура хранения этого не выдержит — задачи ниже надо закрыть **до** того, как база начнёт расти, иначе позже они потянут за собой переделку всех экранов.

**4.П.1. Убрать `persist` из `useDatabaseStore` — жёсткий блокер.**
Сейчас `useDatabaseStore` обёрнут в `persist({ name: 'hr-docs-local-db' })` без `partialize`, то есть **все шесть массивов сущностей целиком сериализуются в localStorage при каждой мутации**. Последствия на боевых объёмах:
- квота localStorage — около 5 МБ. 10 000 сотрудников это уже ~2–3 МБ JSON, а табели (10 000 × 12 месяцев в год, в каждом объект `days` на 28–31 ключ) — десятки мегабайт. Запись упадёт с `QuotaExceededError`;
- каждый клик по ячейке табеля вызывает `updateTimesheet` → полная пересериализация всего стора. При 10 000 строк это заметная блокировка UI на каждый клик;
- это вторая копия данных, которая уже сейчас создаёт риск рассинхрона: SQLite — источник истины, а localStorage переживает перезагрузку и может показать устаревшее до отработки `fetchAll()`. Именно этот механизм маскирует дефект импорта Excel (см. 4.0.8).

Убрать `persist` из `useDatabaseStore` полностью. Источник истины — SQLite, кэш — оперативная память. `useAppStore` (тема, акцент, плотность, шрифт, язык, валюта, сессия) `persist` **сохраняет** — там десяток скалярных полей, это правильный кандидат на localStorage.

**4.П.2. Загружать данные по срезу, а не всё сразу.**
`fetchAll()` тянет все шесть таблиц целиком при каждом входе. Для `employees`, `departments`, `positions`, `templates` это допустимо. Для `timesheets` и `archives` — нет: они растут линейно по времени и по штату. Ввести параметризованные выборки: `listTimesheets(year, month)` и `listArchives({ year, departmentId, employeeId })`, дёргать их при смене фильтра на экране. Оба слоя (`tauriDb.ts` и `server.ts`) правятся одинаково.

**4.П.3. Виртуализация списков.**
Добавить `@tanstack/react-virtual` (в проекте его нет) и применить:
- `Employees` — виртуализация строк таблицы TanStack Table;
- `Timesheet` — критичнее всего: 10 000 строк × 31 ячейка = 310 000 узлов DOM. Виртуализировать строки, sticky-колонки слева и справа сохранить;
- `Archive` и `Reports` — виртуализация либо пагинация, на выбор реализующего.

**4.П.4. Индексы в SQLite.**

## 5. Критерии приёмки (обновлённые)

Приложение считается готовым, когда:

1. Собирается как Windows-инсталлятор (`nsis`/`msi`) через `npm run tauri:build` и работает **полностью офлайн** — без сети, внешнего сервера и внешних шрифтов.
